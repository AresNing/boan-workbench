# Boan 项目管理 Agent 规范 v1

## 1. 宗旨与职责

用户交代目标、补充要求、处理必要决定并验收成果。Boan 负责维护任务、安排执行、衔接上下文、组织验证和保留进度，不要求用户管理会话。

每个项目具有一个逻辑上的管理 Agent，负责整个项目的协调。它由用户输入、执行结果、验证结果和状态变化等事件唤醒，不要求永久运行或永久保留同一个模型会话。

管理 Agent 决定“接下来做什么”，调度程序负责可靠执行并强制检查边界。

## 2. 对象与关系

```text
项目
├─ 项目事实：规则、背景、已确认决定、共享成果
├─ 项目管理 Agent
└─ 任务
   ├─ 目标、要求版本、验收标准、状态、依赖
   ├─ 执行轮次：本轮要求版本、执行记录、验证与交付
   └─ 主执行 Agent
      ├─ 当前执行会话：可以承接多轮工作
      ├─ 历史会话：替换后保留记录
      └─ 辅助 Agent：按需承担有边界的工作
```

- 一个项目有多个任务，任务之间可以建立无环依赖。
- 一个任务同一时间只有一个主执行者，负责整合结果与交付。
- 一个任务可以经历多个执行轮次和会话；会话不与执行轮次一一对应。
- 一个执行会话只服务一个任务。跨任务共享明确的事实和成果。
- 有独立成果、状态与验收边界的工作可以成为子任务；临时调查或检查属于辅助工作。
- 会话切换不改变任务身份，也不清空任务事实。

## 3. 管理原则

### 目标连续

新增输入默认结合当前提交对象和任务背景理解。原目标的补充、纠正和验收反馈继续原任务；独立目标建立新任务。

浏览某个任务不改变输入的提交对象。存在会显著影响执行方向的歧义时，先澄清，继续其他不受影响的工作。

### 要求先保存，再执行

每条补充要求先持久化，再投递给执行者。涉及行为变化时更新要求版本，并保留新增、替代或撤销关系，避免把互相矛盾的要求不断堆叠。

保存成功、投递成功和执行者已接收是不同状态。只有执行者确认接收后，才能向用户表示已纳入当前执行。

### 默认续接，必要时替换

优先在当前主会话继续工作。仅在会话失效、上下文不适用、执行引擎切换或需要隔离时创建新会话，并提供交接记录。

方向变化首先停止受影响的操作，不默认终止所有工作或丢弃已有上下文。

### 自动推进有明确边界

授权范围内、低风险且可逆的工作自动推进。权限批准、关键业务决定和用户验收不能由管理 Agent 代替。

遇到阻碍时，标明阻碍和最小解锁条件，并安排可独立继续的任务。重试必须有次数或时间上限，不允许无条件循环。

### 事实与证据优先

任务状态以实际执行事件为准。请求停止不等于已经停止；模型表示完成不等于验证通过；验证通过不等于用户已验收。

共享结论必须注明来源、适用范围和是否已验证。

## 4. 新输入的处理规则

| 输入或事件 | 管理动作 | 会话策略 |
|---|---|---|
| 补充细节 | 更新要求并投递，在安全节点调整执行 | 复用当前主会话 |
| 与当前方向冲突的修改 | 停止受影响操作，更新要求和计划 | 优先保留主会话 |
| 询问进度、解释结果 | 根据任务事实回答 | 不重启执行 |
| 独立新目标 | 建立新任务，识别依赖 | 执行时建立独立会话 |
| 待验收或已完成后的修改 | 重新打开原任务，启动新一轮工作 | 可用时复用，否则交接 |
| 验证失败 | 分析失败证据，安排有界修复 | 优先复用主会话 |
| 会话失效或上下文需要更换 | 生成交接记录，替换执行会话 | 新会话接手原任务 |
| 用户暂停 | 停止继续调度，取消或等待在途操作结束 | 保留可恢复上下文 |

“安全节点”指当前不可中途打断的操作结束后、下一项受影响操作开始前。若旧操作继续执行会违反新要求，应立即请求中止，并确认实际结果。

## 5. 管理 Agent 可调用的操作

管理 Agent 通过结构化操作提出安排，不直接修改任意任务状态。

| 操作 | 含义 |
|---|---|
| `create_task` | 创建目标、验收标准和初始要求 |
| `revise_task` | 新增、替代或撤销要求，生成新版本 |
| `set_dependency` | 建立或调整任务依赖，禁止依赖成环 |
| `dispatch_task` | 安排符合执行条件的任务 |
| `deliver_update` | 向主执行者投递要求并跟踪接收 |
| `pause_task` / `resume_task` | 请求暂停或恢复 |
| `replace_session` | 通过交接记录替换执行会话 |
| `delegate_work` | 安排有范围、成果和预算的辅助工作 |
| `request_decision` | 提交无法自行决定的具体问题 |
| `request_verification` | 按验收标准安排验证 |
| `submit_delivery` | 提交对应要求版本的成果与证据 |

用户验收由独立的用户操作确认。管理 Agent 不得自行将任务标记为已验收。

每项操作携带操作 ID、目标对象和预期状态版本。调度程序检查权限与前置条件，拒绝过期或重复操作，并返回实际执行结果。

## 6. 状态流转

任务主状态：

```text
待执行 → 执行中 → 验证中 → 待验收 → 已完成
             ↘ 需处理
             ↘ 暂停中 → 已暂停
             ↘ 执行失败
```

- 验证失败且仍可自动修复：回到执行中。
- 自动修复额度耗尽：进入执行失败，保留证据。
- 等待业务决定或权限：进入需处理，并记录具体原因。
- 暂停必须经过实际停止确认，才能进入已暂停。
- 待验收或已完成后收到修改要求：保留历史交付，重新进入待执行。
- 执行中的小幅补充可以保持执行中，但必须更新要求接收状态。
- 应用重启后先核对执行是否仍存活；无法确认的操作不得自动重放。

## 7. 调度程序必须保证的规则

这些规则由程序实现，不能只依靠模型遵守：

1. 同一任务最多有一个有效主执行者；被替换的旧执行者不能继续写入或提交有效交付。
2. 要求、安排和交付先持久化，消息允许重投，但不能导致重复执行。
3. 新要求到达时，检查正在运行的操作及验证；旧版本证据是否仍适用必须明确判断。
4. 提交交付时核对最新要求版本，拒绝过期交付。
5. 并行修改必须有工作区隔离或明确的写入范围；未具备隔离条件时按项目串行执行。
6. 权限由宿主强制执行；取消、超时和暂停必须传播到实际工具。
7. 执行者替换、服务恢复与重试不得重放旧审批，也不能假定外部操作尚未发生。

## 8. 会话交接

交接记录至少包含：

- 当前目标、最新要求版本与验收标准。
- 已确认决定、有效约束和被撤销要求。
- 已完成、未完成与当前阻碍。
- 已修改文件、成果位置及工作区状态。
- 验证证据、失败原因与尚未验证部分。
- 在途或结果不确定的操作。
- 建议下一步。

新执行者必须核对当前文件和在途操作，不能仅凭交接摘要假定现场状态。

## 9. 用户界面

用户看到任务的目标、进展、待处理事项、成果和验收入口。

执行轮次、会话替换、辅助 Agent 和投递细节放入执行记录，按需查看。需要用户处理时，说明具体问题及影响，不要求用户选择“在哪个会话继续”。

## 10. 首期落地与验收

首期保留同项目串行执行，优先实现：

1. 要求版本、替代关系与可靠接收记录。
2. 当前主会话的复用与追加要求。
3. 会话失效后的交接恢复。
4. 最新要求版本与交付证据的核对。

之后再加入任务依赖和隔离条件下的辅助 Agent 并行。

首期必须验证以下场景：

- 执行中补充要求后，仍为同一任务，执行者收到最新要求。
- 方向改变后，旧执行不会继续产生冲突修改。
- 重复投递不会重复创建任务或重复执行操作。
- 会话失效后可以接手，已完成修改与要求不丢失。
- 旧版本验证通过时，不能交付尚未处理的新要求。
- 暂停与重启后，不会误显示仍在执行或自动重放不确定操作。
